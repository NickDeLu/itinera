# Itinera — AI-Powered Travel Itinerary Assistant

Itinera is a full-stack web application that helps travelers plan, organize, and manage their trips
using an AI-powered assistant. You can chat in natural language to create trips and itinerary items,
forward booking emails to build itineraries automatically, review and confirm AI-parsed emails, and
browse your trips on an interactive timeline.

Think of it as a smart travel planner that reads your booking confirmations and organizes your whole
trip for you.

## Features

- **AI Chat Assistant** — Plan trips conversationally. The AI can create trips, add/edit/delete
  itinerary items, look up real places, and answer questions — all through a streaming chat UI
  (Server-Sent Events).
- **Email → Itinerary Automation** — Forward a booking confirmation email (flight, hotel, restaurant)
  to your Itinera inbox. A Mailgun webhook ingests it, an AI extracts the structured details, and it
  is turned into a trip or itinerary items.
- **Review Queue** — AI-parsed emails that need a human decision (or that failed to parse) land in a
  Review screen where you can edit the details or assign them to an existing trip before confirming.
- **Trips & Timeline** — View all your trips and an interactive timeline of each trip's itinerary items.
- **Places Search** — The AI searches real places (restaurants, hotels, attractions, etc.) via the
  Geoapify Places API and presents curated results for you to choose from.
- **Authentication** — Email/password signup & login backed by Supabase Auth with JWT access tokens
  and refresh-token auto-renewal.
- **Trusted Email Whitelist** — Add the email addresses you forward from; only whitelisted senders
  are processed — emails from unknown senders are silently discarded.
- **Responsive UI** — A Svelte 5 single-page app with a sidebar (desktop) / bottom nav (mobile) and a
  welcome onboarding carousel.

## File-by-File Guide

### Backend — entry point & config
- **`src/index.ts`** — The Express server. Sets up CORS, JSON body parsing, serves the built Svelte
  frontend from `frontend/dist`, serves legacy `public/` test pages, mounts all route groups, exposes
  the `/chat` and `/chat/stream` endpoints, and tests the database connection on startup.
- **`src/database.ts`** — Creates the Supabase clients. Exports `supabaseAdmin` (service-role client
  for server-side operations) and `supabaseAnon` (anon client respecting RLS), plus
  `createAuthenticatedClient(jwt)` used by the auth middleware.
- **`tsconfig.json`** — TypeScript compiler settings (`rootDir: ./src`, `outDir: ./dist`, strict mode).

### Backend — AI engine (`src/ai/`)
- **`ChatEngine.ts`** — The heart of the assistant. `runChatLoop` runs a non-streaming multi-turn
  conversation (used by the CLI test script); `runStreamingChat` sends Server-Sent Events
  (`text_chunk`, `turn_start`, `turn_done`, `tool_call`, `tool_result`, `done`, `error`) to the browser.
  It calls Venice AI, parses tool calls, executes them, feeds results back, and formats tool output
  for the model.
- **`StreamProcessor.ts`** — Consumes the raw SSE stream from Venice AI, buffers and parses chunks,
  extracts the plain-text reply plus any tool calls, forwards each text delta for live streaming, and
  enforces a timeout.
- **`ToolCallParser.ts`** — Incrementally parses the streaming JSON response (tracks brace depth) to
  find the complete `{ tools, text }` object emitted by the model.
- **`ToolChainExecutor.ts`** — Executes an array of tool calls for a given user by routing each one
  through the `CommandFactory`, injecting the `user_id` if missing, and collecting results/errors.

### Backend — commands (`src/commands/`)
Each command implements the `Command` interface (`execute(): Promise<any>`). They are the concrete
actions the AI can perform against the database/APIs. `CommandFactory` maps a tool name to the right
command:
- **`Command.ts`** — The shared `Command` interface.
- **`CommandFactory.ts`** — Maps tool names → command instances (the switch that wires the AI to the
  code).
- **`CreateTripCommand.ts`** — Create a new trip.
- **`EditTripCommand.ts`** — Update trip fields (name, destination, dates, description, status).
- **`DeleteTripCommand.ts`** — Delete a trip.
- **`FetchTripsCommand.ts`** — List the user's trips.
- **`CreateItineraryItemCommand.ts`** — Add an activity/flight/hotel/etc. to a trip.
- **`EditItineraryItemCommand.ts`** — Update an itinerary item.
- **`DeleteItineraryItemCommand.ts`** — Remove an itinerary item.
- **`FetchItineraryItemsCommand.ts`** — List a trip's itinerary items.
- **`SearchPlacesCommand.ts`** — Query Geoapify for real places (used by `search_places`).
- **`SaveEmailDataCommand.ts`** — Persist an inbound email for later processing.

### Backend — repositories (`src/repositories/`)
Data-access layer wrapping Supabase queries:
- **`TripRepository.ts`** — CRUD for trips.
- **`ItineraryRepository.ts`** — CRUD for itinerary items + activity-type lookups.
- **`EmailRepository.ts`** — Saves inbound email messages, fetches them, manages the review queue
  (count / list / route-to-review / confirm).
- **`UserEmailRepository.ts`** — Manages the user's trusted-email whitelist and looks up which user a
  sender email belongs to.

### Backend — services (`src/services/`)
- **`VeniceService.ts`** — Wraps the Venice AI chat-completions API (streaming, JSON response format),
  with exponential-backoff retries on transient server errors.
- **`EmailProcessorService.ts`** — Takes a saved email, asks the AI to extract structured trip + item
  data, decides whether to route to review or auto-create, and creates the trip/items accordingly.
- **`GeoapifyService.ts`** — Geocodes locations and searches places via the Geoapify API, mapping a
  user "intention" to recommended place categories.

### Backend — prompts (`src/prompts/`)
- **`systemPrompt.ts`** — The chat system prompt: tells the AI to always respond with strict
  `{ tools, text }` JSON, include `user_id`, describe the available tools and their args, and follow
  workflows (e.g., search places first then ask before creating items).
- **`emailProcessorPrompt.ts`** — The single-turn extraction prompt used to parse forwarded booking
  emails into structured JSON.

### Backend — routes (`src/routes/`)
- **`auth.ts`** — `/auth/signup`, `/auth/login`, `/auth/refresh`, `/auth/me`.
- **`trips.ts`** — `/trips` (list/delete trips, get trip with items).
- **`emails.ts`** — `/emails/review`, `/emails/review/count`, `/emails/:id/confirm`.
- **`userEmails.ts`** — `/user/emails` (list / add / remove trusted email addresses).
- **`mailgun.ts`** — `POST /webhooks/mailgun/inbound` (with optional HMAC signature verification),
  saves the email and kicks off background AI processing.

### Backend — middleware & scripts
- **`middleware/auth.ts`** — Verifies the `Authorization: Bearer <jwt>` token against Supabase and
  attaches the user + an authenticated client to the request.
- **`scripts/test-itinerary-ai.ts`** — An interactive CLI agent for testing the AI loop without the
  web UI (`npm run test:ai`).

### Frontend (`frontend/`)
- **`src/main.js`** — Svelte app bootstrap (mounts `App` into `#app`).
- **`src/app.css`** — Global styles / design tokens.
- **`src/App.svelte`** — Top-level component: handles onboarding, auth state, route switching, and the
  review-count badge.
- **`src/lib/api.js`** — API client (fetch wrapper with JWT auth + auto-refresh) and the SSE chat
  stream reader.
- **`src/lib/NavBar.svelte`** — Sidebar (desktop) + bottom nav (mobile) with the review badge.
- **`src/lib/Icon.svelte`** — Inline SVG icon component.
- **`src/views/Auth.svelte`** — Login / signup screen.
- **`src/views/Chat.svelte`** — The AI chat UI with live streaming and collapsible tool details.
- **`src/views/Trips.svelte`** — List of the user's trips; opens the timeline.
- **`src/views/Timeline.svelte`** — Interactive timeline of a trip's itinerary items.
- **`src/views/Review.svelte`** — Review queue: confirm/edit AI-parsed emails and assign trips.
- **`src/views/Settings.svelte`** — Account settings (profile, log out, trusted emails).
- **`src/views/Onboarding.svelte`** — Welcome carousel shown on first visit / `?onboarding=true`.
- **`vite.config.js`** — Vite config with dev server on port `5173` and a proxy to the backend on
  port `2087`.

### Database & docs
- **`schema.sql`** — The complete reference schema for `users`, `trips`, `activity_types`,
  `email_messages`, `itinerary_items`, `user_emails`, plus all Row-Level Security policies.
- **`migrations/001…` / `002…` / `003…`** — Incremental SQL runs against an already-created database
  (add email body + user_emails table; replace `parsed` with review-status columns; rename to
  `parsed_status`).
- **`schema-diagram.mmd`** — Mermaid ER diagram visualizing the schema relationships.
- **`docs/mailgun-webhook-setup.md`** — Step-by-step Mailgun + Cloudflare Tunnel webhook setup.
- **`public/`** — Legacy standalone test pages (`test.html`, `chat-test.html`) served as static
  files for quick manual testing.
- **`Dockerfile`** — Three-stage build: compiles the Svelte frontend, then the TS backend, then
  serves both from a slim Node 22 runtime image on port `8080`.

## Environment Setup

Create a `.env` file at the project root with the fields below (this file holds all secrets; it is
**not** included in the ZIP and should never be committed). You'll need your own Supabase project
and Venice AI key — see the sections below for where to get each value.

```env
# Server port (defaults to 5000 if not set)
PORT=2087

# Supabase — get from https://app.supabase.com/project/_/settings/api
SUPABASE_URL=https://YOUR-PROJECT-ref.supabase.co
SUPABASE_ANON_KEY=your-anon-key
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key

# Venice AI (LLM)
VENICE_MODEL=qwen3-5-9b
VENICE_AUTH_KEY=your-venice-inference-key

# Geoapify (optional — enables place search)
GEOAPIFY_API_KEY=your-geoapify-key

# Mailgun (optional — only needed for email ingestion)
MAILGUN_API_KEY=your-mailgun-api-key

# Optional: set to "true" to disable public signup
# BLOCK_SIGNUP=false
```

## Database Setup (Supabase)

1. Create a new project at [supabase.com](https://supabase.com).
2. Open the **SQL Editor** and run the contents of **`schema.sql`** to create all tables, seed
   `activity_types`, and install the Row-Level Security policies.
3. If you already had an older version of the schema, run the three files under **`migrations/`** in
   order (`001` → `002` → `003`) to bring the database up to date.
4. Paste your project URL, anon key, and service-role key into `.env`.

## How to Run

### 1. Install backend dependencies
```bash
npm install
```

### 2. Install frontend dependencies
```bash
cd frontend
npm install
cd ..
```

### 3. Run the backend (development)
```bash
npm run dev
```
Starts the TypeScript server on the port in `.env` (`PORT=2087`). On success you'll see:
```
✓ Database connection successful
✓ HTTP API running at http://localhost:2087
✓ Frontend available at http://localhost:2087
```

### 4. Run the frontend (development, with hot reload)
Open a second terminal:
```bash
cd frontend
npm run dev
```
The Svelte dev server runs at **http://localhost:5173** and proxies API calls to the backend on port
`2087` (configured in `frontend/vite.config.js`).

Open **http://localhost:5173** in your browser.

> **Recommended development combo:** keep the backend on `2087` and the frontend dev server on `5173`.

### Running the frontend build via the backend only
If you only want one server, build the frontend and let the backend serve it:
```bash
cd frontend && npm run build && cd ..
npm run dev        # or: npm run build && npm start
```
Then visit **http://localhost:2087** — the backend serves the compiled Svelte app directly.

### Production build & run
```bash
npm run build       # compiles TS -> ./dist
npm start           # node dist/index.js
```

### Run with Docker
A multi-stage `Dockerfile` builds the frontend + backend and serves everything on port **8080**:
```bash
docker build -t itinera .
docker run -p 8080:8080 --env-file .env -e PORT=8080 itinera
```
(The `-e PORT=8080` after `--env-file` is important: the `.env` sets `PORT=2087`, which would
otherwise make the server listen on the wrong port inside the container.)
Then open **http://localhost:8080**.

## How It Works

1. **Sign up / log in.** Supabase Auth issues a JWT stored in the browser (auto-refreshed).
2. **Chat.** In the Chat screen you describe a trip or booking. The request hits `/chat/stream`, the
   AI (Venice) streams back a `{ tools, text }` JSON plan, the `ToolChainExecutor` runs any commands,
   and results stream back to the UI as SSE events for a live, typewriter-style response.
3. **Places.** When you ask about restaurants/attractions, the AI calls `search_places` (Geoapify),
   shows you results, and *waits* for you to pick before creating any itinerary items.
4. **Email automation (optional).** You whitelist your email in Settings, then forward booking emails
   to your Itinera inbox. Mailgun posts them to `/webhooks/mailgun/inbound`, which saves the message
   and lets the AI parse it in the background. Confident parses become trips/items automatically;
   uncertain ones go to the Review queue.
5. **Review & Trips.** Confirm anything flagged for review, then browse your trips on the timeline.

## API Endpoints

| Method | Path                          | Auth | Description                                   |
|--------|-------------------------------|------|-----------------------------------------------|
| POST   | `/auth/signup`                | –    | Register a new user                           |
| POST   | `/auth/login`                 | –    | Log in, returns access + refresh tokens       |
| POST   | `/auth/refresh`               | –    | Refresh access token                          |
| GET    | `/auth/me`                    | ✔    | Current user profile                          |
| GET    | `/trips`                      | ✔    | List the user's trips                         |
| GET    | `/trips/:id`                  | ✔    | Get one trip with its itinerary items         |
| DELETE | `/trips/:id`                  | ✔    | Delete a trip                                 |
| GET    | `/emails/review`              | ✔    | List emails in the review queue               |
| GET    | `/emails/review/count`        | ✔    | Review-queue count (nav badge)                |
| POST   | `/emails/:id/confirm`         | ✔    | Confirm / save a reviewed email               |
| GET    | `/user/emails`                | ✔    | List trusted email addresses                  |
| POST   | `/user/emails`                | ✔    | Add a trusted email                           |
| DELETE | `/user/emails/:id`            | ✔    | Remove a trusted email                        |
| POST   | `/chat`                       | ✔    | Non-streaming chat (returns all turns)        |
| POST   | `/chat/stream`                | ✔    | Streaming chat (SSE)                          |
| POST   | `/webhooks/mailgun/inbound`   | –    | Mailgun inbound webhook (HMAC-verified)       |

(There is no REST endpoint for updating a trip — trip edits are done through the AI's `edit_trip`
tool via chat. `userEmails` uses DELETE `/user/emails/:id`.)

## Email Processing (Mailgun)

To enable "forward an email → itinerary":

1. Whitelist the email address you forward **from** in the app's Settings.
2. Run a tunnel to your local server (see `docs/mailgun-webhook-setup.md`):
   ```bash
   npm install -g cloudflared
   cloudflared tunnel --url http://localhost:<PORT>
   ```
   Replace `<PORT>` with the port your backend is running on — the `PORT` value from your `.env`
   (e.g. `2087`), or `8080` when running via Docker.
3. In the Mailgun dashboard, create a receiving route that POSTs to:
   ```
   https://<your-tunnel>.trycloudflare.com/webhooks/mailgun/inbound
   ```
4. Forward a travel booking email to your Itinera inbox. The webhook saves it, the AI extracts
   structured data, and (depending on confidence) it either creates the trip/items or lands in the
   Review queue.

## Troubleshooting

- **`Missing Supabase environment variables…`** — Ensure `.env` exists with `SUPABASE_URL`,
  `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`.
- **`Database connection test failed`** — Check the Supabase URL/keys and that `schema.sql` was run.
- **Port already in use** — Change `PORT` in `.env` (and update the proxy in
  `frontend/vite.config.js` if you move off `2087`).
- **Chat returns errors / 401** — Make sure `VENICE_AUTH_KEY` and `VENICE_MODEL` are set, and that
  you're logged in (token is sent automatically).
- **Places search fails** — Set `GEOAPIFY_API_KEY` and confirm your location string is geocodable.
- **Review badge shows old count** — The count refreshes when you navigate to Review; it updates on
  login and after confirming items.
- **Emails not being processed** — Verify the Mailgun route URL ends in `/webhooks/mailgun/inbound`,
  the sender email is whitelisted, and the tunnel is running.
